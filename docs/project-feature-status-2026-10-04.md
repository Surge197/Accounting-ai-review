# Accounting AI Review — feature and progress report

**Assessment date:** 4 October 2026  
**Overall stage:** Functional prototype undergoing integration and reliability work; not ready for production use.

This report describes the current local source code and the checks run in this chat. “Implemented” means the feature has code behind it, not that its complete user journey has passed acceptance testing. No live Tally, Zoho, or AI-provider connection was tested. There is insufficient milestone history to measure development speed or give a defensible completion percentage.

## Current features

### 1. Single-company accounting review — implemented, acceptance testing pending

- Choose TallyPrime or Zoho Books as the source format.
- Set company name and review dates, upload transactions, and run a review.
- View transaction counts, issue counts, flagged amounts, and individual findings.
- Group findings as Critical, Requires review, or Observation, with reasons and suggested actions.

The current changes remove preloaded demo transactions and start the application with an empty client list.

### 2. File imports and normalization — implemented, data-quality validation pending

- CSV, Excel (.xlsx/.xls), XML, and JSON parsing.
- Tally XML and Zoho-oriented normalization into a shared transaction structure.
- Fields for voucher number, date, party, ledger, debit/credit, amount, tax components, GSTIN, and source information.
- Upload flows for individual reviews and client-specific data.

The Excel reader uses the first worksheet. Support for a file extension does not guarantee that every export layout will map correctly; representative customer files still need testing.

### 3. Accounting checks — implemented as deterministic rules

The interface describes an “18-rule” review. The implementation groups several numbered checks into shared conditions. It covers:

- Duplicate invoice/voucher numbers and possible repeated transactions.
- Unusually large vendor/customer transactions compared with other entries for that party.
- Missing GSTIN and GSTIN format checks.
- GST calculation and tax-component inconsistencies.
- Negative transaction values.
- Suspense/unallocated account postings.
- Large journal adjustments and a cash-payment threshold check.
- Missing counterparties or narrations.
- Round-number transaction patterns.

These are the checks present in the code. Their thresholds and tax-related wording have not been independently validated in this assessment. The findings are generated by the rule engine; AI is used to add explanations.

### 4. Multi-client review — implemented, acceptance testing pending

- Add and remove clients with company, GSTIN, software, industry, and group details.
- Select clients and run batch reviews, rerun reviews, or retry failed clients.
- Display progress and per-client collection/review logs.
- Show a client risk matrix and consolidated portfolio totals.
- Filter combined findings by client, severity, software, issue type, and search text.
- Open individual client results from the portfolio.

Risk labels use simple rules based on finding counts, rather than a trained risk model. Client lists, transactions, reports, and snapshots currently live in React memory; no durable accounting-data storage or reload recovery is wired into this workflow.

### 5. Change tracking — implemented within the current session

- Compare newly collected transactions with a previous client snapshot.
- Identify added, modified, deleted, and unchanged transactions.
- Record changes to amounts, tax fields, ledgers, GSTIN, and descriptions.
- Retain up to five snapshots per client in application state.

This is snapshot comparison, not a completed resumable incremental-sync system. Its history is lost when the application state is reset or the page reloads.

### 6. AI explanations and portfolio summaries — partially integrated

- Backend support for Gemini and OpenAI explanation requests.
- Executive portfolio-summary endpoint.
- Deterministic fallback explanations and summaries when external AI is unavailable.
- AI connection-test and configuration controls.

Finding enrichment sends at most 15 findings to the backend provider per request. Ordinary review requests do not forward the selected provider/model, so the backend defaults to Gemini. Provider selection therefore needs end-to-end wiring and verification. Live provider availability was not checked.

### 7. Reports and exports — implemented, output validation pending

- Single-company report preview.
- Excel workbook containing the review and analyzed transactions.
- Master Excel workbook with portfolio summary, consolidated findings, and client worksheets.
- Browser print / Save as PDF flows for individual and consolidated reports.

The PDF buttons invoke browser printing; there is no dedicated PDF-generation service. Export formatting and reconciliation against input files still need acceptance testing.

### 8. Zoho Books — partial live integration

Code exists to test a connection and request invoices, bills, credit notes, vendor credits, customer/vendor payments, expenses, and journals using an access token.

Current limits matter for completeness:

- Each resource request stops after three pages of 200 records: up to 600 records per resource.
- Failed resource requests can be skipped while the combined response still reports success.
- The `fullSync` option does not implement an incremental cursor in the backend.
- Several master-data and balance methods return empty values.
- Transaction normalization is simplified; for example, fetched tax totals are split equally into CGST and SGST with IGST set to zero.
- A complete OAuth authorization/refresh lifecycle is not implemented.

The source shows a collection foundation, but reliable, complete Zoho accounting imports have not been established.

### 9. Windows Tally connector — tested foundation; accounting sync absent

Implemented capabilities include pairing, heartbeats, online/offline status, company discovery, company permissions, preflight jobs, retries, lease handling, duplicate-job protection, SQLite persistence, Windows credential protection, rotating logs, and Windows service scripts.

The automated connector suite passes all 18 tests, including Windows credential-protection round trips and local protocol fixtures.

The connector does **not** transfer accounting transactions. `SYNC_ACCOUNTING` explicitly returns “not implemented.” The old direct Tally endpoints are disabled, while the accounting UI still targets them. Real Tally compatibility, Windows service installation/reboot, and TSplus session behavior require testing on the actual server.

## Current blockers and reliability gaps

1. **Incomplete demo-data cleanup:** Ten application type-check errors remain in `src/clients/defaultClients.ts`, which still refers to removed sample-data types.
2. **Integration settings cannot currently save through the existing form:** The form always includes a Tally settings object, but the server rejects any such payload before applying the other settings. This also obstructs saving AI/Zoho settings through that form.
3. **No persistent client review workspace:** Client data, reports, and snapshots need durable storage and restoration.
4. **Live Tally collection is missing:** The service foundation must be connected to a scoped accounting export/import workflow and to the UI.
5. **Zoho completeness and mapping need work:** Pagination limits, suppressed resource failures, token refresh, and tax/transaction mappings need correction and tests.
6. **Review accuracy needs targeted tests:** If no transactions match the selected dates, the rule engine falls back to reviewing all transactions. Flagged amounts sum findings, so a transaction with multiple findings can be counted more than once. New clients also default to an April 2024 review period.
7. **Application access control is unfinished:** The connector has separate operator/agent authorization, but the wider settings, AI, and Zoho routes do not have an application user/tenant permission layer.

These findings come from source inspection, not a full security audit or browser acceptance run.

## How the project is progressing

The project has moved beyond a screen-only demo: its review workflow, rule engine, portfolio aggregation, exports, and connector infrastructure all contain substantial implementation. The connector foundation has the strongest automated verification.

The work is now at the point where integration and correctness determine usefulness. Recent local changes focus on removing demonstration data, but that cleanup is incomplete. The next milestone should be a dependable file-based review from upload through validated export, followed by complete live integrations and deployment acceptance.

Recommended sequence:

1. Clear the ten type errors and repair the settings-save mismatch.
2. Fix date filtering and define whether flagged totals count unique transactions or findings; validate imports and exports against known examples.
3. Add durable client/report storage and application authentication/permissions.
4. Complete one live integration end to end, with explicit completeness/error reporting.
5. Run real-server Tally/TSplus tests and full browser acceptance tests before deployment.
